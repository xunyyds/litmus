# 08 · 覆盖度评估

> 状态：v0.2 ｜ 最后更新：2026-11-10
> 本文件解决：**「该检测的都检测到位了吗」——用数据回答，包括没做到的部分。**
> 数据来源：`python tools/coverage.py`（从 `schema/vectors.json` 与 `probes/*.java` 实时计算）。

---

## 0. 一句话结论

**签名 / 重打包这条线是硬的；运行时完整性是中上；注入类一半靠特征；设备面（root / 模拟器 / 多开）基本只能到「可疑」。**

而最大的问题**不是向量数量不够**，是一件更根本的事：

> **这些检测从来没有在真实注入环境下被验证过。**
> 我们跑过的 10 次真机运行，全部是「干净包」和「换签名重打包」。
> Frida、LSPosed、Zygisk 一条都还没实测 —— 也就是说，注入类向量的灵敏度目前是**理论值**，不是实测值。

这一点必须先说，否则下面的覆盖度数字会被误读成「我们已经能抓 Frida」。

## 1. 目录 vs 实现

| 类别 | 目录 | 已实现 | 待实现 | tier A | tier B | tier C | **可下结论（A+B）** |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 运行时完整性 `runtime-integrity` | 15 | 12 | 3 | 4 | 10 | 1 | **14** |
| 注入痕迹 `injection` | 9 | 7 | 2 | 0 | 3 | 6 | **3** |
| 包完整性 `package-integrity` | 10 | 9 | 1 | 6 | 3 | 1 | **9** |
| 提权面 `privilege` | 8 | 7 | 1 | 2 | 0 | 6 | **2** |
| 虚拟化/多开/模拟器 `virtualization` | 6 | 5 | 1 | 0 | 1 | 5 | **1** |
| 环境面 `environment` | 5 | 5 | 0 | 1 | 0 | 4 | **1** |
| **合计** | **53** | **45** | **8** | **13** | **17** | **23** | **30** |

读法：**`A+B` 才是「能判死」的向量数**。tier C 只能到「可疑」（契约 §2.2 的硬约束，有 CI 门禁守着）。
所以这张表最该看的是最后一列，而不是「53 条」。

## 2. 三种能力，分开说

### 2.1 能判死的（A/B，30 条）

| 能力 | 代表向量 | 实测状态 |
| --- | --- | --- |
| 换签名 / 重打包 | `pkg.signature` `pkg.signing.v3` `pkg.cert.history` `pkg.codepath.hash` `pkg.zip.fingerprint` | ✅ **已验证**（`C2-repack` 5 条全部坐实，包完整性 100→36.1） |
| 函数入口被改（inline hook） | `inj.elf.inline` | ⚠️ **阴性已验证**（干净进程扫 4056 个入口 0 命中），**阳性未测** |
| GOT 劫持 | `rt.got.integrity` | ⚠️ 同上（147 槽 0 异常） |
| ptrace 附着 | `rt.tracerpid` | ✅ 阴性已验证 |
| 匿名可执行段 / memfd | `rt.maps.anon_exec` `rt.memfd` `rt.maps.exec_files` | ✅ 阴性已验证（并已修掉 ART JIT 的误报） |
| syscall 侧信道 | `rt.vdso` `rt.timing` | ⚠️ 只有基线数据（`openat` 中位 681ns），**判定阈值待实测** |

### 2.2 只能到「可疑」的（C，23 条）

提权面 6/8、虚拟化 5/6、环境面 4/5 都是 C 级。这不是实现偷懒，是设计判断：
「装了 Magisk 但没授权」「模拟器但没作弊」都真实存在，C 级判死就是误报机器。
代价是：**这三类永远压不下去分数，也永远抓不死人**。

### 2.3 测不了的（UNKNOWN，实测 4 条）

| 向量 | 为什么测不了 |
| --- | --- |
| `rt.maps.file_integrity`（Java 侧兜底） | Android 12+ `/proc/self/mem` 被 SELinux 拒（`open` 直接 ENOENT）。native 侧 `inj.elf.inline` 已用 mmap 绕过这个限制，但这条 Java 兜底仍是 UNKNOWN |
| `inj.proc.env` | `/proc/self/environ` 不可读 |
| `pkg.codepath.hash` / `pkg.zip.fingerprint` | 设计如此：APK 哈希烘不进自己，交 CLI 平面判（**CLI 侧确实判出来了**） |

## 4. 8 条缺口，逐条说影响

| 向量 | tier | 不实现会怎样 |
| --- | --- | --- |
| `rt.art.entrypoint` | A | **最疼的一个**。Java 层 hook（Xposed/LSPlant）目前只能靠 `rt.stack.frames` 这种 B 级旁证，拿不到「方法入口指针被改」的直接证据 |
| `rt.maps.cross_view` | B | maps 可能被内核态工具整体伪造，现在只有单一路径读取，无法交叉验证 |
| `rt.signal.handlers` | B | 改 `SIGTRAP/SEGV` handler 是对抗调试检测的常见手法，现在看不见 |
| `inj.loader.solist` | B | 手工映射的 so（不走 `dlopen`）会同时躲过 `inj.module.paths` 与 maps 路径检查 |
| `inj.dex.inmemory` | B | 内存加载的 dex（热修复、动态加载壳）目前只能靠 `pkg.dex` 间接推断 |
| `priv.caps` | A | 借 su 提权的进程能力位异常，现在只能靠 `priv.su` 这种 C 级特征 |
| `pkg.split` | B | 只替换某个 split APK 的定向篡改，**完全没有检测** |
| `virt.vapp.binder` | B | 容器代客调用时 uid 错位是 VirtualApp 的硬特征，现在抓不到 |

## 5. 明确没覆盖的（不在目录里，也没打算在 v0.2 做）

这一节比上面那张表更重要 —— **知道边界在哪，比多堆 20 条特征有用**。

| 攻击面 | 为什么没做 | 影响 |
| --- | --- | --- |
| **内核态 hook / KPM / eBPF** | 需要内核模块，且我们的检测跑在用户态，改 `/proc` 就能骗 | 面对改内核的对手，`rt.*` 系列会整片失效（只剩 `rt.timing` 的统计痕迹） |
| **硬件断点 / 单步** | 不落字节、不改 GOT，`inj.elf.inline` 看不见 | 高级调试与部分注入器可以完全隐形 |
| **页表重映射 / shadow page** | 要读页表或做内存完整性树，成本超出 v0.2 | 硬件辅助 hook 能同时骗过字节比对与匿名段检测 |
| **TEE / Play Integrity / Key Attestation** | 需要服务端与厂商证书链 | 拿不到「设备未被解锁」的硬件级证明，只能软检测 |
| **加固壳自身（梆梆/爱加密/360）** | 那是壳的能力，不是我们的靶场 | 不评估壳强度，只评估「你的补丁能不能过我们的检测」 |
| **证书固定 / 网络面** | 属于传输安全，不属于篡改面 | 与本品定位无关，故意不做 |
| **ART 编译产物校验（JIT/AOT）** | 要解析 `OatFile` 与 JIT code cache 归属 | 改编译产物的 hook 目前只能靠 `rt.maps.anon_exec` 间接覆盖 |
| **探针自身被改** | 部分覆盖（`rt.maps.file_integrity` 能看自家 `.so` 正文） | 对手若改 `liblitmusprobe.so` 的**数据**而非代码，仍可能骗过 |
| **服务端重放** | 本地方案（见 `00-定位与边界.md` §3.1） | 完整重放一份干净报告，我们挡不住 |

## 6. 所以，到位了吗

**按攻击手法数：14 项里 13 项有向量，但只有 1 项做过完整的「注入 → 检出」闭环验证（重打包）。**

具体打分（10 分制，主观但可争论）：

| 面 | 分 | 理由 |
| --- | ---: | --- |
| 重打包 / 签名 | 9 | A 级密码学判定，CLI 平面兜底，实测坐实 5 条 |
| 运行时完整性 | 7 | 不变量设计正确，但阳性对照缺失、ART 层没打通 |
| 注入痕迹 | 5 | 向量多但一半靠特征，且从未在真 Frida 下验证 |
| 提权面 | 4 | 全 C 级，误报换来的只是「可疑」 |
| 虚拟化 / 多开 | 3 | 5/6 是 C 级，模拟器改个属性就过 |
| 环境面 | 3 | 本质是「使用姿势」而非「篡改」 |

## 7. 下一步该做什么（按性价比）

1. **阳性对照自测（最高优先）** —— 这是本轮暴露的最大问题。
   做法：给靶包加一个**只在 debug flavor 存在**的「自伤模式」（广播触发，native 里对自己的一个函数做 inline hook + 改一个 GOT 槽），
   然后看 `inj.elf.inline` / `rt.got.integrity` 是否真的翻红。
   **如果连自己制造的 hook 都抓不到，那前面所有「不变量」的说法都只是纸面推理。**
2. 补 3 条 A/B 缺口：`rt.art.entrypoint`（Java hook 直接证据）、`inj.loader.solist`（手工映射库）、`pkg.split`（零覆盖）。
3. 真机注入实测：在 `10AF8D0K2R00A0F` 上装 frida-server，把这 4 类注入各跑一遍，把实测值填进本文件 §2.1 的「阳性未测」格子。
4. 设备面那 12 条 C 级：按 `docs/05` 的结论，往**交叉视图**方向改，而不是继续加特征。

> 本文件所有「未测」标记都是诚实欠账，不是修辞。补齐它们之前，请不要把 Litmus 当成「已经能抓 Frida」的工具。
