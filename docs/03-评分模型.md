# 03 · 评分模型

> 状态：v0.1 ｜ 最后更新：2026-11-10
> 本文件解决：**分数是怎么算的、为什么这么算、以及怎么读它**。

权威实现：`cli/litmus_score.py`。App 侧 `core/Score.java` 用同一套公式做即时摘要，**不做基线归一与盲区判定**。

---

## 1. 从「一条结论」到「一个分数」

```
Signal(id, category, verdict, confidence, weight, tier)
   │
   │  verdict → 污染度 s
   ▼
类别分 C_k  ──  加权平均（按 weight，剔除不可计数项）
   │
   ▼
总分 raw  ──  按类别权重 a_k 聚合
   │
   ▼
归一 adj  ──  减掉干净基线本来就有污染（可选）
```

### 1.1 单条 signal 的污染度

| verdict | s | 计入分母 | 说明 |
| --- | --- | --- | --- |
| `TAMPERED` | 1.0 | ✅ | 确认被改 |
| `SUSPECT` | 0.5 | ✅ | 有痕迹，证据不足（tier C 的默认上限） |
| `CLEAN` | 0.0 | ✅ | 未发现 |
| `UNKNOWN` | — | ❌ | 本设备/本版本测不了 |
| `ERROR` | — | ❌ | 探针自身炸了 |
| `FLAKY` | — | ❌ | 多次采样不一致（v0.2 启用多轮采样） |

**为什么 UNKNOWN 不计入分母**：测不了不等于干净。把它算成 0 会系统性抬高分数（假安全），
把它算成 1 会冤枉（假警报）。唯一诚实的做法是**单独统计并在报告里显式列出**。

### 1.2 类别分

```
C_k = 100 × (1 − Σ_{i∈k, countable} w_i·s_i / Σ_{i∈k, countable} w_i)
```

- `w_i` 是向量的 weight（1–5），由契约里每条向量的定义固定，**不随运行变化**；
- 一个类别里若没有任何可计数信号 → `C_k = null`，且该类别**不参与**总分聚合（不是 0 分，也不是 100 分）。

### 1.3 总分

```
raw = Σ_k a_k·C_k / Σ_k a_k        （只对 C_k ≠ null 的类别求和）
```

默认权重（profile `standard`）：

| 类别 | a_k | 为什么这个权重 |
| --- | --- | --- |
| `runtime-integrity` | 0.24 | 最硬、最难伪造、最能反映「进程被插桩」 |
| `injection` | 0.22 | 直接对应注入类攻击 |
| `package-integrity` | 0.20 | 密码学判定，但只覆盖「静态改动」 |
| `privilege` | 0.14 | 误报最高（ROM 差异大），权重压低 |
| `virtualization` | 0.10 | 只在特定场景相关 |
| `environment` | 0.10 | 兜底面 |

profile 变体：
- `sig-only`：只有 `package-integrity` 计权（验签名场景快速回归）
- `runtime`：`runtime-integrity` 与 `injection` 各 0.5

## 2. tier 怎么用

tier 不是装饰，它约束了**允许出现的 verdict**：

| tier | 允许 | 不许 | 理由 |
| --- | --- | --- | --- |
| A | CLEAN / TAMPERED / SUSPECT / UNKNOWN | — | 不变量或密码学，成立就是定论 |
| B | CLEAN / TAMPERED / SUSPECT / UNKNOWN | — | 交叉视图，判 TAMPERED 时应有第二条证据 |
| C | CLEAN / SUSPECT / UNKNOWN | **TAMPERED** | 特征匹配，误报不可控 |

`confidence` 是**该条结论自身的置信度**，只用于报告展示与排序，**不进公式**。
理由：把一个自评的置信度乘进分数，等于让实现者自己决定权重，分数就不可比了。
真正的权重只有 `weight` 和 `a_k` 两个，都写在契约里、可被外部审计。

## 3. 盲区（Blind Spot）——本产品的核心产出

**定义**：本次运行中，证据表明**包确实被改过**，但某个类别里**一条都没抓到**（该类别 CLEAN 率 100%）。

判据（三条任一成立即「包被改过」）：
1. CLI 平面 `pkg.codepath.hash` = TAMPERED（APK 内容哈希 ≠ 构建期期望）
2. CLI 平面 `pkg.zip.fingerprint` = TAMPERED（ZipEntry 指纹 ≠ 期望）
3. App 平面 `pkg.signature` = TAMPERED（证书 ≠ 期望）

输出：

```jsonc
"blindSpots": [
  {"category": "injection",
   "why": "pkg-modified-but-category-clean",
   "text": "包已改动，但 injection 类 9 条向量全部 CLEAN",
   "score": 100.0, "counted": true,
   "vectors": ["inj.frida.port", "inj.elf.rwx", "…"]}
]
```

- `counted`：本次 profile 下该类别权重为 0 时为 `false` —— 漏检事实成立，但不影响总分（`sig-only` 场景）。
- 与误报的对称关系：盲区是「该抓没抓到」，误报是「不该抓却抓了」。两者都只在**有外部参照**时才有意义
  （盲区靠 CLI 平面证明包被改过，误报靠 baseline 证明环境本来如此）。

**为什么这条重要**：它把「工具没检出」拆成了可归因的两件事——
「**被测者藏得好**」还是「**我们这条判据根本没用**」。前者是能力，后者是缺陷，必须分开看。

## 4. 基线归一（Baseline Normalization）

**问题**：MuMu 模拟器上 `ro.debuggable=1`、`/system` 是 overlay 挂载、`priv.su` 命中——这些不是你改的。
不处理的话，任何人在这台机器上都是 0 分，工具失去区分度。

**做法**：先在**干净状态**（靶包未修补）跑一次，得到 `raw_baseline`，再算：

```
P  = 1 − raw / 100            # 本次污染比例
Pb = 1 − raw_baseline / 100   # 环境固有污染比例
adj = 100 × (1 − max(0, P − Pb) / max(1e-9, 1 − Pb))
```

性质（可验证，`litmus.py selftest` 覆盖）：

| 情况 | 结果 |
| --- | --- |
| 本次与基线一样脏 | `adj = 100`（环境脏不算你的账） |
| 本次比基线更干净 | `adj = 100`（不比干净机更差就是满分） |
| 基线本来就 100 | 退化为 `adj = raw`（无可减） |
| 基线 60，本次 30 | `adj = 100 × (1 − 0.7/0.4 )` → 截断到 0 |

**注意**：归一后的分数**只反映「相对这台机器」的增量**，跨机器不可比。
所以 `run.json` 里同时保留 `raw` 与 `baseline` 引用，报告里两个数都打印。
**做趋势对比时必须同一台机器、同一份基线。**

## 5. 误报（False Positive）

**定义**：给了 `--baseline` 时，满足全部三条：
1. 该向量在基线上就是 TAMPERED（环境固有）；
2. 本次仍是 TAMPERED；
3. 包没被改（CLI 两条平面信号都 CLEAN）。

→ 判为该环境固有问题，**不扣本次的分**，只在报告里标注，并输出 `noiseFromBaseline` 清单。

这条规则的实际价值：拿 MuMu 跑时不至于满屏红；换到真机基线后，同一份代码分数立刻变得有区分度。

---

## 6. 稳定性（v0.2 启用多轮采样）

同一次运行跑 N 轮（默认 3），逐向量比对：

- 3 轮一致 → 正常；
- 不一致 → `FLAKY`，不计分，报告标「该检测不可靠」。

**为什么值得单独做**：`rt.timing` 这类统计判据天然有抖动；`rt.got.integrity` 在 ART 并发编译时可能瞬态异常。
把 FLAKY 显式暴露出来，比让它随机影响分数要好得多——用户会看到「这条别信」，而不是「分数怎么忽高忽低」。

---

## 7. 怎么读这个分数

| 分数 | 含义 | 典型场景 |
| --- | --- | --- |
| 100 | 未检出任何篡改 | 干净安装的靶包 |
| 85–99 | 有弱痕迹，无硬证据 | 装了 LSPosed 但没启用模块 |
| 60–84 | 至少一类被坐实 | 换了签名 / 改了 dex |
| 30–59 | 多类被坐实 | 重打包 + 注入 |
| 0–29 | 全面暴露 | Frida attach + 重签名 + 跑在模拟器 |
| `null` | 分母为 0 | 所有向量都 UNKNOWN（native 没加载 / 权限全缺）—— **这是故障，不是安全** |

**第 5 行的 `null` 是这套模型最重要的一条**：分数算不出来时，我们绝不返回 100。

---

## 8. 已知局限

1. **权重是主观的**。`a_k` 与 `w_i` 都是人为设定。我们把它写死在契约里并公开，是为了「可比」而不是「客观」。
2. **基线归一牺牲了跨机器可比性**。要跨机器比较，用 `raw`。
3. **tier C 的天花板是 SUSPECT**，所以 `injection` / `privilege` / `virtualization` 三个类别在无罪证时很难把分数压到 60 以下——这是刻意的：**宁可漏，不可冤**。
4. **本地方案挡不住重放**（见 `00-定位与边界.md` §3.1）。
5. **`confidence` 不进公式**，所以它只影响阅读体验，不影响分数——如果你不同意某条向量的权重，改契约里的 `weight`，别改 `confidence`。
6. **盲区目前不区分「检测能力缺失」与「与本次修补无关」**。纯重打包会改签名/内容，但不会改模拟器特征，
   于是 `virtualization` / `environment` 会稳定被判成盲区（实测 `C2-repack` 就是这两类）。
   这两件事在语义上完全不同：前者是我们的洞，后者只是「这次没动到」。
   **v0.2 修法**：按 `--framework` 给一个「本次应期待的类别集」（`repack → pkg+rt`、`frida → inj+rt`、
   `lsposed → inj+rt+pkg`），盲区只在期待集内报警，其余降级成「不适用」。
   `run.json` 里的 `blindSpots[].why` / `weight` 字段已为此预留，加规则不用改 schema。
