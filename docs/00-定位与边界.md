# 00 · 定位与边界

> 状态：v0.1 ｜ 最后更新：2026-11-10
> 本文件解决：**这产品到底卖什么、不卖什么、以及为什么这么切**。

---

## 1. 一句话定位

> **一个「防篡改靶场 + 记分器」：我们发布正常包，你任意修补，我们量化告诉你还能看见多少。**

三个角色：

| 角色 | 这是什么 | 谁在用 |
| --- | --- | --- |
| **靶包 canary** | 我们发布的普通 Android 应用，内嵌检测内核 | 想验证「我的修补方案能不能过检测」的人 |
| **检测内核 core** | `io.litmus.core`，6 类 53 条向量 | 也可以整体搬进**你自己的应用**当加固 SDK |
| **记分器 cli** | adb 驱动 + 评分 + 盲区 + 报告 | 做回归的人 / CI |

---

## 2. 要解决的四个真实痛点

对照 Momo / Ruru 这一类「环境检测 App」，我们观察到四个结构性缺口：

### 2.1 只有结论，没有量化
红绿灯无法回答「我把签名校验绕了，但 native 段完整性还过不去，总体算几分」。
→ **Litmus Score（0–100）+ 六个类别分**，且公式公开（见 03）。

### 2.2 不可复现、不可回归
没人能回答「上一版 XPatch 在这台机器上是几分，这一版呢」。
→ 每次运行产出稳定 schema 的 `run.json`，可以 `diff`、可以进 CI、可以画趋势线。

### 2.3 误报无解
模拟器、定制 ROM、开发机上天生「脏」（`ro.debuggable=1`、`/system` 是 overlay 挂载），
一旦判死，分数全红，工具就废了。
→ **基线归一（baseline normalization）**：先跑一次干净机，把「这台机器本来就脏的部分」减掉，
分数只反映**你这次额外引入的污染**。这是与 Momo 类工具最本质的差别。

### 2.4 检测能力是黑盒，无法证伪
工具说「没检出」，你无法判断是「你藏得好」还是「它根本没这条判据」。
→ **盲区矩阵**：强制列出「包确实被改、但这一整类一条没抓到」的类别。
工具的能力边界被自己暴露出来，这是可被外部审计的设计。

## 3. 三个平面与「可信度分级」

这是全项目的核心取舍。**检测器自己跑在被修补的包里**，所以它的一切结论都可能是伪造的。

```
Plane SELF  ── 进程内。看得深，但可被 hook 伪造。
Plane DEVICE ── 设备面。看得广，但误报高。
Plane CLI   ── 进程外。看得「浅」（只有 APK 文件 + 期望值），但**包改不了**。
```

由此得到一条铁律：

> **凡是可能在进程内被伪造的结论，都不能单独作为最终判据。**

落实为三条工程规则：

1. **App 只产出「事实」与「带 tier 的结论」**，`tier` 显式标注证据强度（A/B/C，见 04 §2.2）。
2. **密码学级别的判定放在 CLI 平面**：APK 内容哈希、ZipEntry 指纹、签名链，都拿构建期烘进去的期望值在进程外比对。
3. **报告里保留原始 facts**，任何人可以拿 `report.raw.json` 自己复算——不信任我们的分数也能用我们的数据。

### 3.1 我们能防什么、不能防什么（写在明面上）

| 能力 | 说明 |
| --- | --- |
| ✅ 防低成本伪造 | 改 `report.json` 里的 `verdict` 字段会被 CLI 用 `facts` 交叉验证发现；改 `facts` 里的 APK 哈希要同时骗过签名与 zip 指纹 |
| ✅ 防「只 hook 检测函数」 | 不变量类向量读的是内存字节与磁盘字节，hook 判定函数没用；要过就得 hook `open`/`read`/`mmap` 这一层，成本立刻上升一个量级 |
| ❌ 防不住完整重放 | 攻击者把整份 `report.json` 换成干净机录的。要解决必须引入服务端 nonce + 硬件密钥证明（v0.3） |
| ❌ 防不住「改内核」 | 内核态 hook 可以把 `/proc/self/maps` 全改掉。这类对抗超出本工具目标（但 `rt.timing` 会留下统计学痕迹，属 tier B 佐证） |

**产品定位不接受「绝对安全」这种说法**——我们卖的是「可量化、可回归、能自我审计」，不是「不可绕过」。

## 4. 威胁模型

### 4.1 我们假设的攻击者

| 能力 | 假设 |
| --- | --- |
| 能改 APK | ✅ 重打包、换签名、改 dex、改 so、改清单 |
| 能在进程内注入 | ✅ Frida / Xposed / LSPosed / Zygisk / 自研 inline hook |
| 能改应用私有目录 | ✅ 改 `Android/data/io.litmus.canary/` 下的产物 |
| 能改 ROM | ⚠️ 部分假设（v0.1 不做内核对抗） |
| 能改本机 CLI 产物 | ❌ 不在威胁模型内（那是「评测者作弊」，不是「被测者作弊」） |

### 4.2 我们不假设的

- 不假设设备已 root（检测必须在非 root 下也能跑）。
- 不假设有网络（全程离线，`INTERNET` 权限都不申请）。
- 不假设厂商 ROM 干净（→ 基线归一）。

## 5. 与「金丝雀验收」的关系

XPatch 已有的 `tools/canary`（见 `review/83-金丝雀验收.md`）解决的是**单点验收**：
「签名校验这一层到底过没过」，7 条 V1–V7 判据，硬指标清晰。

Litmus 是它的**上一层**：

| | XPatch tools/canary | Litmus |
| --- | --- | --- |
| 范围 | 签名校验 7 条 | 六类 53 条（签名只是其中一类） |
| 判定 | 脚本比对期望值 | 三平面 + 评分 + 盲区 |
| 产物 | 一份 log | `run.json`（可回归、可对比） |
| 使用者 | 框架开发者自己 | 框架开发者 + 修补方案作者 + 客户 |

设计上直接继承了它两个经过实战的结论（`83` 号文档）：
1. **期望值必须在构建前烘进去**（签名密钥固定 → 证书哈希可预知；APK 自身哈希不可能）；
2. **清单里那个 `appComponentFactory` 占位属性**——逼手工打包器走「替换值」而不是「新增属性」分支（`Litmus/canary/AndroidManifest.xml` 已沿用）。

## 6. 非目标

明确不做，避免产品发散：

- ❌ 不做「一键过检测」的绕过工具（我们是尺子，不是锤子）
- ❌ 不逆向第三方加固厂商的具体实现（只做通用不变量）
- ❌ 不做云端沙箱 / 大规模设备农场（v0.4 只做 CI 接入）
- ❌ 不收集任何用户数据

---

## 7. 合法边界

靶包 `io.litmus.canary` 是我们自己发布的、不含第三方代码的测试应用。
所有检测只针对**这个靶包自身**与**本机环境**，不读取其它应用的私有数据（`QUERY_ALL_PACKAGES` 仅用于匹配框架包名，属 tier C 弱信号）。

用途限定：自研加固/壳/补丁框架的回归验收、教学、CTF、安全研究。
禁止：绕过第三方真实保护、未授权修改他人应用。
