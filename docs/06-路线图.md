# 06 · 路线图

> 状态：v0.1 ｜ 最后更新：2026-11-10
> 本文件解决「每个版本做到什么算完成」：四档版本的**范围边界**与**可判定验收标准**（命令 + 硬指标 + 判定方）。凡是不能跑出 PASS/FAIL 的条目，不写进这里。

---

## 0. 主线

| 版本 | 一句话目标 | 平面 | 向量 | 出口条件 |
| --- | --- | --- | --- | --- |
| **v0.1**（当前） | 单包两平面跑通、CLI 能记分 | self + device | 7 已实现 / 48 已定义 | 干净基线 0 误报、0 篡改 |
| **v0.2** | 跨应用检测 + 基线归一 + 框架适配器 | self + device + cli | ≥40 实现 | 4 档框架盲区 ≤1 |
| **v0.3** | 自动布防测试台，出「绕过成本」曲线 | 全三平面 + 测试台 | 48 | 曲线可复现、单调性成立 |
| **v0.4** | CI 化 + 与 XPatch 发布门禁联动 | 全 | 48 | 门禁能拦住退化 |

向量口径：`04-契约.md` §3 冻结 40 条 + `02-探针目录.md` 新增 8 条 = **48**。README/契约正文写的「38 向量」是历史目标值，与 §3 实际条目数不符，已在 `02-探针目录.md` §5「待契约澄清」记录，本文件按 48 排期。

## 1. v0.1 · 单包两平面（当前）

**范围。** ① 靶包 `canary`（手工 aapt2+d8+apksigner 构建，无 gradle）内嵌 `io.litmus.core`；② self 平面 7 条向量 + device 平面（同进程内的设备面读数）；③ CLI `litmus.py` 记分、出 `run.json`/`report.md`/`report.html`；④ 三份 schema 可用。

**不在范围内。** 跨应用检测（需要 v0.2 的独立 detector APK）、基线归一、框架适配器、多轮采样、native 的 `inlineHook`/`gotCheck`/`memfd` 精化（T2 的 TODO）。

| # | 验收项 | 命令 / 操作 | 硬指标 | 现状 |
| --- | --- | --- | --- | --- |
| V1.1 | 构建可复现 | `pwsh -File canary\build.ps1` 连跑两次 | 两次 `build-info.json` 的 `zipFingerprint` **逐字节相同**（契约 §4.4 刻意不含时间戳；`apkSha256` 允许因 zip 元数据不同而变） | 待实测 |
| V1.2 | 环境自检 | `python cli\litmus.py doctor` | 返回码 0；缺 adb/设备/构建产物时返回码非 0 且有具体缺失项 | 待实测 |
| V1.3 | 干净基线 | `litmus.py run --label C0-baseline` 于干净机 | `summary.tampered == 0`；`falsePositives` 条数 ≤ 1；`score ≥ 85`（目标值待标定） | 待实测 |
| V1.4 | 基线向量生效 | 同上 | 7 条 `v0.1 基线` 向量**全部**出现在 `signals[]`，`verdict ∈ {CLEAN, UNKNOWN}`，不出现 `ERROR` | 待实测 |
| V1.5 | 分数可复现 | 同机连跑 3 次 | 三次 `score` 极差 ≤ 3；同名向量 `verdict` 一致率 100%（无 `FLAKY`，v0.1 无多轮采样，出现即算失败） | 待实测 |
| V1.6 | 篡改可判 | 用不同 key 重签靶包后重装再跑 | `pkg.signature` = `TAMPERED` 且 `score` 相比 C0 下降 ≥ 15 | 待实测 |
| V1.7 | schema 合法 | `run.json` / `report.json` 过 `schema/*.json` | 校验器返回 0，无 additionalProperties 违规 | 待实测 |
| V1.8 | 汇总产物 | `litmus.py matrix --runs runs` | 生成跨 label 的对比表；行 = run，列 = 6 类分 + 总分 | 待实测 |

**v0.1 已知缺口**（如实记，不假装完成）：`rt.maps.anon_exec` 的 JIT 阈值未标定（实现里用 0.6/0.8 两档 confidence 兜）；`rt.timing` 无阈值来源；native 的 `memfd`/`inlineHook`/`gotCheck` 字段在契约 §4.5 里已定义但无数据。

## 2. v0.2 · 独立 detector APK + 基线归一 + 适配器

**范围。** ① 把 `io.litmus.core` 拆成独立 detector APK，能对**任意** `packageName` 出包面/设备面读数（`PackageInfo`/codePath/签名/清单/split 安装面 + 设备属性），**不读目标进程内存**——Android 10+ `/proc/<pid>/maps` 跨 uid 不可读（`01-总体架构.md` ADR-2），内存面仍由内嵌内核提供，两个进程对同一事实各看一次构成**互证**；② 向量补齐到 ≥40 条，每类 ≥4 条；③ 多轮采样（`FLAKY` 落地）；④ 基线归一（干净机先跑 C0，只算增量）；⑤ 框架适配器：11 个方案（`05-框架适配矩阵.md` §2）的 `hints()`，仅 tier C。

> 因此 v0.2 的 `report.json` 对「外部包」调用的必然是子集：`rt.*`/`inj.*` 一类需要进程内视角的向量应为 `UNKNOWN`（不计分），而不是伪造 CLEAN。这条边界写进 V2.2 的判定里。

| # | 验收项 | 硬指标 | 判定方 |
| --- | --- | --- | --- |
| V2.1 | 向量覆盖 | 53 条中 **≥45 条**有实现并通过自测；六个类别每类 ≥4 条 | 向量注册表 vs 清单 diff，空行 = 失败 |
| V2.2 | 跨应用检测 | 对 3 个第三方包（含 1 个 split 包、1 个 ≥200MB 包）能出完整 `report.json`；单包耗时 ≤ 2s；`rt.*`/`inj.*` 全部为 `UNKNOWN` 且不计入分母（不许伪造 CLEAN） | 脚本 + 逐条断言 |
| V2.3 | 多轮采样 | 每向量 3 轮；一致率 <2/3 → `FLAKY`；`FLAKY` 不计分且单独计数 | 单元测试（构造抖动探针） |
| V2.4 | **适配器不许判死** | 断言：只注入 C 类命中（无 A/B）时，`verdict` 必须 ∈ `{SUSPECT}`；改恒等为 `TAMPERED` 的构建必须让测试**红** | 负向测试（negative test） |
| V2.5 | 基线归一 | 同一框架档、3 台干净设备，归一后 score 标准差 ≤ 5 | 3×3 实测 |
| V2.6 | 误报率 | 3 台干净真机 + 2 台模拟器，`falsePositives` 总数 ≤ 2（≈ 53 条里的 4%） | 脚本 |
| V2.7 | 盲区 | `frida`/`zygisk`/`lspatch`/`xpatch` 四档，每档 `blindSpots` ≤ 1 条 | `run.json` 的 `blindSpots[]` |
| V2.8 | 覆盖率矩阵 | 输出 53 向量 × 11 框架的命中矩阵（CSV）；**空格必须能解释**（写进 `05` §6 的待实测表） | 人工评审 |

V2.4 是这一档的**门禁级**条目：它把契约 §5 的硬约束变成一条会失败的测试，而不是一句注释。

## 3. v0.3 · 自动布防测试台（绕过成本曲线）

**范围。** 用 XPatch 内核的 `deploy()`（契约 §5 第 2 项）自动把各 hook 引擎/框架布防到靶包上，自动跑 Litmus，产出「布防强度 → 分数」曲线。这是本项目**唯一**的核心产出：把「过检测」变成一条可比的成本曲线，而不是红绿灯。

最小布防矩阵：`frida`(注入/gadget) / `lsposed` / `zygisk` / `kernelsu` / `vapp` / `lspatch` / `hook-engine` × 设备 ≥2 台（A12 + A17）。

| # | 验收项 | 硬指标 | 判定方 |
| --- | --- | --- | --- |
| V3.1 | 全自动布防 | 单框架布防 + 安装 + 跑分 ≤ 120s，全程无人工键鼠操作 | 计时器 |
| V3.2 | 布防可复现 | 同框架同设备连跑 3 次，报告一致性 ≥ 90%（向量级 verdict 相同比例） | diff |
| V3.3 | 曲线产物 | 产出 `cost-curve.csv`：`framework, step, vector, verdict, score`；每框架 ≥1 条曲线 | 文件存在 + schema 校验 |
| V3.4 | **单调性** | 对同一框架，随布防步骤递增（0→N），`score` **单调不增**（允许 Δ 噪声 ≤ 2）；违反即 FAIL 并列出反例向量 | 断言 |
| V3.5 | 曲线可区分 | `frida` 与 `zygisk` 两条曲线的末端 score 差 ≥ 10（若 <10 说明向量没抓住差异面，属盲区） | 断言 |
| V3.6 | 绕过成本定义 | 每框架给出「从 TAMPERED 打到 CLEAN 的最少步数 × 每步人工分钟」；人工分钟列必须标注 `待实测`，不得编造 | 评审 |
| V3.7 | 攻击侧无回归 | 布防失败（框架没生效）必须被判定为 `ERROR`/`UNKNOWN`，不得静默变成「CLEAN=已过检测」 | 负向测试 |

V3.7 是这一档最容易犯的错：**布防脚本报错 = 分数很好看**。必须让「测试台自己失败」显式可见。

## 4. v0.4 · CI 化 + XPatch 发布门禁联动

**范围。** ① GitHub Actions 流水线（matrix job）；② 真机云接入（≥3 台真实设备，API 差异化）；③ 与 XPatch 发布门禁联动：XPatch 的每个对外版本都必须跑 Litmus 并留下趋势数据；④ 回归门禁。

| # | 验收项 | 硬指标 | 判定方 |
| --- | --- | --- | --- |
| V4.1 | 触发即跑 | push / PR 触发；单次流水线 ≤ 25min（3 机型 × 2 API 并行） | Actions 时长 |
| V4.2 | 产物齐全 | 每次跑出 `run.json` + `report.html` + `matrix.csv` 三件套，作为 artifact 保留 ≥30 天 | 产物检查 |
| V4.3 | PR 注释 | 每次 PR 自动贴一条评论：总分、相对基线的 Δ、新增盲区、新增误报 | Actions |
| V4.4 | **发布门禁** | 对 `xpatch` profile：新版本在同一框架档下 `score` 不得下降超过 2（= 不得让检测更容易被绕过）；超限需 PR 说明并把差额写入盲区基线 | 门禁脚本（非 0 退出） |
| V4.5 | 回归门禁 | 在 C0（干净机）上出现任一向量 `CLEAN→TAMPERED` 即 FAIL（误报回归），或 `TAMPERED→CLEAN`（判据变弱）即 FAIL | 门禁脚本 |
| V4.6 | 趋势可见 | 能出 30 天 score 趋势（按框架分线）；数据来自 `runs/` + artifact，不依赖人工表格 | 报告页 |
| V4.7 | 真机云 | ≥3 台真实设备（A12/A14/A17 各一），无人工介入；设备不可用时流水线 `UNKNOWN` 而非 PASS | Actions |

## 5. 依赖关系与不可跳过的前置

| 要做什么 | 前置（做不到就别开工） |
| --- | --- |
| v0.2 跨应用检测 | V1.5（分数可复现）必须先绿，否则跨应用噪声无法与实现缺陷区分 |

## 6. 明确不做（Out of scope，防止范围漂移）

- **服务端 nonce / 硬件密钥证明**（v0.5+）。本地方案能挡低成本伪造，挡不住完整重放——这条写在 README 的边界里，不在本路线图内。
- **kernel 级对抗**（KernelSU 的 umount 隐藏、内核模块 hook）。Litmus 是应用层+CLI 层方案；内核面的隐蔽性只在 `priv.*` 的 C 类里体现，不投入 A 类研发。
- **第三方真实应用的保护绕过**：靶包是我们自己发布的 `canary`，不针对任何第三方应用。见 README 的「合法使用」。
- **闭源判据**：向量判据全部写在 `02-探针目录.md`，不做「黑盒打分」。
