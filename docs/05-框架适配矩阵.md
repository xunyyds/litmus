# 05 · 框架适配矩阵

> 状态：v0.1 ｜ 最后更新：2026-11-10
> 本文件解决「换一种修补方式，Litmus 期望看到什么」：把每个框架/方案映射到**痕迹面 → 命中向量 → 强度**，并给出 CI 里该跑哪几条向量。它是 v0.2 框架适配器（`deploy()`/`hints()`，契约 §5）与 v0.3 自动布防测试台的输入。

---

## 0. 读法与硬约束

| 符号 | 含义 |
| --- | --- |
| `●` | 该方案**必然**产生此痕迹；有 tier A/B 向量可判 |
| `○` | 常见但取决于实现/版本；多数只能到 tier C |
| `—` | 该方案通常不留此痕迹（不投入检测成本） |
| `?` | `待实测`，见 §6 |

三条硬约束（先写在前面，避免后面被误读成「特征表」）：

1. **适配器只能产生 tier C 弱信号**（契约 §5）。`hints()` 输出包名/端口/线程名，只用于把 `evidence` 写得更可读。
2. **任何一条「框架名匹配」都不能单独判 TAMPERED。** 判死必须由 A/B 向量给出，见 §4。
3. 本文件的矩阵描述的是**痕迹的存在性**，不是「命中即判脏」。装了 LSPosed 的手机上跑一个干净包，矩阵里的 `○` 依然会被看到，但它只能是 SUSPECT。

**XPatch 行是本文件的自我校准点。** 它做了过签（`pkg.signature`/`pkg.signing.v3` 会被 L1/L2 归一化回 CLEAN，见 `review/83-金丝雀验收.md` C2/C3 实测），但 `pkg.zip.fingerprint`/`pkg.codepath.hash` 在 CLI 侧读文件本身，改不到。所以「过签成功」在 Litmus 上等价于「A 类少 2 条、还剩 3 条」——这是矩阵里唯一一行我们**确知实现细节**的，也是检验判据是否诚实的标尺。

## 4. 为什么框架名匹配不能判死

契约 §2.2/§5 的硬约束在此展开成三条理由：

1. **「装了」不等于「用了」。** 一台开发机上装着 LSPosed、frida-server、KernelSU 是常态；被检测的包可能一根头发都没被改。若允许 C 判死，这个正常态会被打成 TAMPERED——而 Litmus 的核心指标之一就是**误报率**（`run.json` 的 `falsePositives[]`）。
2. **特征是可被单方面改的，不变量不是。** LSPosed 的 manager 包名可改、Frida 的端口可配（`-l`）、gadget 的文件名可改。任何一条靠「名字」的判据，其失效成本是**对方的配置项**；而 `rt.maps.file_integrity` 的失效成本是「不 hook」。
3. **判死会污染别的框架的读数。** 允许「包名命中 → TAMPERED」意味着矩阵里所有 `○` 的行都能直接把分数打穿；模拟器上 5 条 `virt.*` C 类全红会让「干净基线」失去意义，基线归一（README「三个平面 / 基线归一」）这套设计会直接失效。

落地的门槛建议（具体聚合规则以 `03-评分模型.md` 为准）：

| 结论 | 需要什么 |
| --- | --- |
| `CLEAN` | 全类 A/B 向量等式成立 |
| `SUSPECT` | 任意 tier C 命中，或单个 B 单独命中 |
| `TAMPERED` | ≥1 条 tier A 命中，或同一痕迹面上 ≥2 条 tier B 互证 |

适配器的两份接口因此被限死在契约 §5 的形态：`hints()` 只出 C；`deploy()` 只在测试台内用（自动布防 → 跑分 → 出曲线），绝不进产品路径。

## 5. CI 推荐矩阵（按框架实测该跑哪几条向量）

用于 v0.2/v0.3 的回归：每行是一次 `litmus.py run --framework <id>`，`profile` 决定跑全量还是子集（全量 53 条约 400–600ms，子集 <100ms，`待实测`）。

| 框架 | profile | 必跑向量 | 期望最少命中 | 明确不跑（误报高） | 出口判据 |
| --- | --- | --- | --- | --- | --- |
| `frida` | inject | `rt.tracerpid` `rt.maps.anon_exec` `inj.loader.solist` `rt.memfd` `inj.frida.port` | 3（含 ≥1 条 A/B） | `rt.timing` | 至少 1 条 A 或 2 条 B 命中 |
| `frida-gadget` | inject | `rt.maps.anon_exec` `rt.maps.file_integrity` `pkg.zip.fingerprint` `pkg.signature` | 2 | `inj.frida.port`（gadget 无端口） | 同上 |
| `lsposed` | inject | `rt.art.entrypoint` `rt.maps.file_integrity` `rt.maps.deleted` `rt.stack.frames` | 2 | `inj.frida.port` | 同上 |
| `zygisk` | inject | `rt.maps.deleted` `inj.module.paths` `rt.maps.file_integrity` | 2 | `priv.props` | 同上 |
| `kernelsu` | device | `priv.caps` `priv.mounts` `priv.kernel` `priv.selinux` | 1 | `virt.multi.user` | C 命中只出 SUSPECT |
| `vapp` | inject | `virt.vapp.binder` `inj.dex.inmemory` `virt.vapp` | 1 | `virt.emulator.*` | ≥1 条 B |
| `emulator` | device | `virt.emulator.props` `virt.emulator.files` `virt.emulator.hardware` `rt.maps.anon_exec` | 2 | 全部 `priv.*`（出厂即脏） | 只允许 SUSPECT + 基线归一 |
| `xpatch` | full | `pkg.codepath.hash` `pkg.zip.fingerprint` `pkg.manifest` `rt.art.entrypoint` `rt.maps.file_integrity` | 2 | —（这是我们自己的标尺，全跑） | `pkg.*` 的 A 类必须命中；否则视为盲区 |
| `lspatch` | full | `pkg.signature` `pkg.zip.fingerprint` `rt.art.entrypoint` | 2 | — | 同上 |
| `hook-engine` | inject | `rt.art.entrypoint` `rt.maps.file_integrity` `rt.got.integrity` | 2 | `pkg.installer` | 同上 |

矩阵的读法：**「期望最少命中」是下限而不是上限**——命中更多不是更好，可能意味着判据太松（误报）。真正要盯的是 `run.json` 的 `blindSpots[]`：**包确实被改了、但某类一条都没抓到**，那才是缺口。

## 6. 待实测

| 项 | 无法先写死的原因 |
| --- | --- |
| XPatch 行的「匿名段 / 线程名 / GOT」三格 | 取决于 `xp/hook_core.so` 的注入方式（解包到 cache 再 `dlopen` vs 从 apk 内加载），需读一次实测 maps |
| LSPosed 的 `匿名段` 格 | LSPlant 的 trampoline 落在合法 `.so` 内还是匿名段，随 Android 版本与 `libart` 布局变化 |
| KernelSU/APatch 的 `属性`/`包名` | 各版本隐藏策略差异大；KernelSU 的 umount 模式可把应用可见的挂载表清干净 |
| Frida gadget 的 `端口` | 可配置 `listen` 接口，默认不开；不能作为必现痕迹 |
| 各 profile 的实际耗时（100–600ms 区间） | 需在 A12/A17 各一台真机上量 |
| 模拟器上 `virt.*` C 类的实际命中率 | 决定基线归一的系数与 CI 出口判据 |
| `hook-engine` 一行的 `GOT` 格（Pine/SandHook/Whale） | 三者实现不同（Whale 有 PLT hook 分支），需分别实测 |
