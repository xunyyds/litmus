## 1. 怎么读这张表

| 列 | 含义 |
| --- | --- |
| `id` | 与契约 §3 逐字一致；`新增` = 本文件按同一命名规则补的（`04-契约.md` §3「新增向量：先加到本文件，再用这个 id 实现」） |
| `类别` | 契约 §2.1 六类之一，必须与 id 前缀一致（`rt.`/`inj.`/`pkg.`/`priv.`/`virt.`/`env.`） |
| `tier` | A = 不变量/密码学；B = 交叉视图；C = 特征匹配（**只许出 SUSPECT**，契约 §2.2） |
| `权重` | 1–5，**只表达类内重要性**（`Score` 按 `pollutedWeight / countedWeight` 聚合）；跨类聚合权重 `a_k` 见 `03-评分模型.md` |
| `判据` | 一句话不变量。写成「A 必须等于 B」而不是「检测 X 的特征」 |
| `依赖` | `native` = 需 `liblitmus_probe.so`；`java` = 纯 Java/反射；`adb` = CLI 平面判（App 侧只给事实）；`+root` = 无 root 只能出 UNKNOWN（不计分）。本列不出现 `root` 即表示无 root 需求（契约口径写作 `-`） |
| `状态` | `v0.1 基线` = 已实现；`v0.2 计划` = 未实现 |

三条口径约束（容易被写歪的地方）：

1. **判据必须能写成等式**。写不出等式的一律降级为 tier C，并只作为 A/B 的解释性佐证。
2. **tier A 不允许「证据不足下 TAMPERED」**（契约 §2.2）；A 类实现的失败路径只能 `unknown()`，不能 `suspect()`。
3. **native 已采集的事实 ≠ 已实现的向量**。`04-契约.md` §4.5 的 `memfd`/`deleted`/`threads`/`inlineHook`/`gotCheck` 里，v0.1 实际只有 `threads`/`anonExec`/`rwx`/`tracerPid`/`vdsoSize`/`timing` 有值（`inlineHook`/`gotCheck`/`memfd` 精化是 T2 的 TODO）。所以 `rt.memfd`、`inj.elf.inline`、`rt.got.integrity` 的状态是 `v0.2 计划`，即便字段已存在。

## 3. 分类详注

### 3.1 runtime-integrity（13 条，类内权重 46）

**为什么不容易被绕过。** 这一类的判据全是「等式两侧」：一侧由内核/链接器提供（maps、映射字节、GOT 槽值、入口指针），一侧来自磁盘文件或第二条读取路径。要绕过不是「把自己藏起来」，而是**让等式重新成立**——那等于把 hook 撤掉。类内成本最高的两条是 `rt.maps.file_integrity`（禁止任何 inline hook）与 `rt.art.entrypoint`（禁止任何 Java 层入口 hook）。两者同时满足的框架只剩「数据面 hook」（改字段值/改返回值），而数据面 hook 的稳定性与覆盖面远低于入口 hook，成本曲线因此陡增。

**典型绕过手法。** ① 把 trampoline 塞进已映射的合法 `.so`（「so 内留洞」），再对齐 maps 里的文件名——被「映射文件名 ↔ 磁盘文件」绑定校验挡住，且副本只能以匿名或 private 方式映射（撞 `rt.maps.anon_exec`）；② hook `open`/`read` 让磁盘侧也读到改后字节（自证同源）——这正是 `rt.vdso` 与 `rt.maps.cross_view` 存在的原因：至少一条路径必须走裸 `syscall`；③ hook 掉 maps 的**解析**而不是内容——三路径逐行比对覆盖；④ 只 hook 我们自己的探针类——探针检自身 `ArtMethod` 入口异常即命中 `rt.art.entrypoint`（自指检测）。

**已知误报源。** `rt.maps.anon_exec` 在现代 ART/WebView（JIT code cache、`libjitloader`）与 Flutter/RN 的 JIT 上天然非零；`rt.memfd` 会被部分厂商图形栈使用；`rt.timing` 在低端机/热节流下抖动极大；`rt.stack.frames` 在 R8 混淆 + 内联折叠后取不全。**这四条都不是 tier A**，就是因为必须靠「基线归一」压误报（先跑干净基线，只算增量）。

**两处 `待实测`。** `rt.maps.file_integrity` 的可执行段粒度（4K 页 vs ELF 段）与 `rt.art.entrypoint` 在不同 ROM 的 `ArtMethod` 布局偏移，都必须在 A12/A17 各一台真机上实测后再定判据阈值。

### 3.2 injection（8 条，类内权重 26）

**为什么不容易被绕过。** 注入的物理前置动作只有一个：**把一段不在磁盘上的代码放进进程并执行**。Frida、Zygisk、加固壳、热修复，都要么造匿名可执行段、要么造不在 linker 链里的模块、要么造内存 dex。这三件事各有独立观测面（maps / `dl_iterate_phdr` / `DexFile` 链），且**互相不能同时伪装**：把模块注册进 linker 链就得给出真实路径（撞 `inj.module.paths`），不注册就撞 `inj.loader.solist`；dex 落盘就得在 `codePath` 内（撞 `pkg.*` 的 A 类），不落盘就撞 `inj.dex.inmemory`。

**典型绕过手法。** Frida 切 gadget 模式后端口向量失效，但匿名段/memfd 仍在；Zygisk 模块「加载完卸载原文件」留下 `(deleted)`（`rt.maps.deleted`）；加固把 dex 解密到内存（`inj.dex.inmemory`）；把 trampoline 写进已有 `.so` 的 `.bss` 再 `mprotect` → 与 `rt.maps.file_integrity` 交叉（`.bss` 不在 `r-x`，改为可执行即留下非法的段权限组合）。

**已知误报源。** `inj.elf.rwx` 在部分 GPU/ART 驱动加载期有短暂 RWX → 必须在稳定期采样（进程起来 ≥ 2s）；`inj.frida.port` 在本机装有 frida-server 但目标进程未被注入时必报；`inj.module.paths` 对 x86 上跑 ARM 的转译层（`libhoudini`/`libndk_translation`）必报。

**边界。** `inj.frida.port`/`inj.frida.socket`/`inj.module.paths`/`rt.thread.name` 刻意留在 tier C：**装了 frida-server ≠ 这个进程被注入了**，只能出 SUSPECT。真正判死靠 `rt.maps.anon_exec` + `rt.maps.deleted` + `rt.maps.file_integrity` 的组合。

### 3.3 privilege（7 条，类内权重 21）

**为什么不容易被绕过。** 提权面的判据不是「有没有 root 工具」，而是两个更强的命题：`priv.caps` 看**内核是否给本进程记了额外能力**（应用进程 `CapEff` 必须全 0，这是内核不变量，不是启发式），`priv.mounts`/`priv.props` 看**挂载与属性是否仍与出厂一致**。root 方案为了隐藏自己必须 umount、改 props，这些动作本身留痕，于是形成「藏得越深、痕越多」的反向压力。

**典型绕过手法。** KernelSU 的 umount 模式能把 self 的 mount 表清干净 → `priv.mounts` 失效，但与 `/proc/version`、`getuid`、capability 的交叉仍在（`待实测`：各版本差异大，不能写死）。Magisk 的 DenyList/Zygisk 主要针对注入侧隐藏，不改 capability，所以对 `priv.caps` 无效。

**已知误报源。** 部分国产 ROM 出厂即有 `/system/xbin/su`；工程机/内测机 `ro.debuggable=1`；permissive 的内测机撞 `priv.selinux`；`virt.multi.user` 与 `priv.mounts` 在「系统自带双开/工作资料」的 ROM 上出厂即命中。所以这一类**全为 tier C**，只做解释与佐证；「设备脏」不能直接推出「应用脏」（`env.debuggable` 是与 `priv.props` 互证的 A 类锚点）。

### 3.4 package-integrity（9 条，类内权重 33）

**为什么不容易被绕过。** 这是唯一**进程外可判**的类：CLI 拿构建期期望值（`apkSha256`/`certSha256`/`zipFingerprint`）与设备上的包比对，App 侧被 hook 也不改变结论。这是分数的最终权威——三平面设计（README「三个平面」）的地基就在这 3 条 `adb` 依赖的向量上。

**典型绕过手法（本例即 XPatch 自己）。** 过签能让 `pkg.signature`/`pkg.signing.v3`/`pkg.cert.history` 全部回到 CLEAN（`review/83-金丝雀验收.md` C2/C3 实测 9/9 PASS）；但 `pkg.codepath.hash` 与 `pkg.zip.fingerprint` 在 CLI 侧读**文件本身**，除非做 `openat` 级别重定向（L3 深度模式，属另一个平面）。于是「过签成功」在 Litmus 上等价于「A 类少 2 条、还剩 3 条」——这正是本项目要量化的东西，而不是要消灭的现象。

**已知误报源。** `pkg.installer` 在 `adb install`/侧载/商店三态下本来就不同（出厂即如此）；`pkg.signature` 换签名档（fpa/XPatch/轮换）时必须先更新 build-info，否则「期望值过期」会被误读成篡改；`pkg.split` 在厂商做 ABI split 裁剪的机型上与完整包不一致，期望值需按设备 ABI 生成。

**与 `review/83` 的对齐点。** `pkg.signature`（旧 flags）与 `pkg.signing.v3`（新 API）**必须是两套期望值**：轮换包上前者返回 lineage 最老证书、后者返回当前证书（83 §4.1 实测）。写进一条判据里会永久误报。

### 3.5 virtualization（6 条，类内权重 18）

**为什么不容易被绕过。** 容器/多开的本质是「你的代码跑在别人的进程里」，所以 `Process.myUid()` 与 PMS 记录的自身 uid 会错位（`virt.vapp.binder` 抓的就是这个等式）；模拟器的本质是「硬件与架构是伪造的」，`Build` 指纹、qemu 文件、硬件特征三面**同时**异常的概率远高于单面。

**典型绕过手法。** VirtualApp 系可以 hook `Process.myUid()` 让之一致（成本上升，且 Binder 侧归属仍要对齐，见 `virt.vapp.binder`）；模拟器去特征是成熟产业（改 props、删 `/dev/qemu_pipe`、伪造传感器），所以这三条 `virt.emulator.*` **只能做分母**。

**已知误报源。** 云手机/串流方案必命中 `virt.emulator.hardware`；系统自带双开必命中 `virt.multi.user`；这些都是「环境天生脏」。实现上必须让基线归一把「环境脏」与「你额外引入的脏」分开，否则模拟器上这一类会整类全红。

### 3.6 environment（5 条，类内权重 12）

**为什么不容易被绕过。** `env.debuggable` 是 A 类里成本最低的一条：`FLAG_DEBUGGABLE` 是清单里的位，重打包常为了调试方便打开它——改了就是改了，且与 `priv.props` 的 `ro.debuggable` 互为佐证（一个看包、一个看设备，正好是交叉视图的正例）。其余四条观测的是「用户主动开了什么」。

**边界。** 这四条不改代码、只改使用姿势；对抗它们的方法不是 hook 而是「关掉」。所以它们的价值是**解释分数**（说明这台机器上为什么某些向量是 SUSPECT），不是判死。四条的权重都压到 2，就是为了不让「公司 Wi-Fi 有代理」这种环境把总分打穿。

**已知误报源。** `env.proxy` 在公司网络/抓包环境必命中；`env.capture` 在 TalkBack、第三方输入法、自动化测试框架下必命中；`env.overlay` 在游戏加速器/录屏悬浮窗下命中。

## 4. 为什么这些判据与框架无关

### 4.1 不变量 vs 特征匹配，本质是「谁在定义命中」

| 维度 | 特征匹配（`检测 Frida 的 xxx 特征`） | 不变量（`A 是否仍等于 B`） |
| --- | --- | --- |
| 观测对象 | 「像不像某个已知框架」 | 「某一组物理量是否还相等」 |
| 命中条件 | 我们**预先想到了**这个框架 | 对方**做了动作** |
| 新框架的成本 | 加一条规则，O(框架数) 增长 | **0**，等式不变 |
| 对方的对抗手段 | 改名、换端口、去特征 → 我们失明 | 只能是「不 hook」→ 放弃功能本身 |
| 误报来源 | 装了 ≠ 用了 | 只在等式真的不成立时命中 |
| 结论上限 | tier C（契约 §2.2） | tier A/B |

一句话：特征匹配把「识别」的责任放在**我们**身上（我们要认识每一个新框架）；不变量把责任放在**对方**身上（他要么不动，要么等式崩）。前者是军备竞赛，后者是物理约束。

### 4.2 五类框架 + 重打包：必须破坏的等式

不需要为每个框架写判据，只需要问「他要实现功能，物理上必须改什么」。

| 方案 | 必须做的动作 | 必然破坏的等式 | 命中的向量 | 强度 |
| --- | --- | --- | --- | --- |
| **Frida** | ptrace 注入 / gadget `dlopen` / 分配 trampoline 池 | 进程内出现匿名可执行段；`TracerPid≠0`；模块不在 linker 链里 | `rt.tracerpid` `rt.maps.anon_exec` `rt.memfd` `inj.loader.solist` | A/B |
| **LSPosed / Xposed** | 改 Java 方法入口（LSPlant inline hook） | 函数入口指针不再指向 libart；栈帧出现影子帧；模块 `.so` 出现在 maps | `rt.art.entrypoint` `rt.stack.frames` `rt.maps.file_integrity` | A/B |
| **Zygisk + Magisk** | 从 zygote 注入、模块 `dlopen` 后卸载原文件 | maps 出现 `(deleted)` 的可执行段；模块路径出白名单 | `rt.maps.deleted` `inj.module.paths` `rt.maps.file_integrity` | B/A |
| **KernelSU / APatch** | 内核态 su + umount 隐藏 | 挂载表被改写；`/proc/version`、capability 遗留 | `priv.mounts` `priv.caps` `priv.kernel` | C/A |
| **VirtualApp / 双开** | 客应用跑在宿主进程里、代客调 PMS/Binder | `Process.myUid()` ≠ PMS 记录的自身 uid | `virt.vapp.binder` `virt.vapp` | B/C |
| **模拟器（MuMu/AOSP）** | 硬件与架构伪造 | Build 指纹、qemu 文件、硬件特征三面同时异常；ARM 转译层多一层 | `virt.emulator.props` `virt.emulator.files` `virt.emulator.hardware` | C |
| **重打包 / 换签名** | 改 APK 内容或签名块 | 签名链与 ZipEntry 顺序必变 | `pkg.signature` `pkg.zip.fingerprint` `pkg.codepath.hash` | A |

### 4.3 一个等式，一类框架

把五类放在一起看，**它们共同破坏的等式只有五组**——不需要逐个框架匹配特征，只需要守住这五组：

1. **进程内不得有匿名可执行段**：Frida 的 trampoline 池、Zygisk 模块的跳板、加固壳的壳代码都只能落在 `file` 为空且带 `x` 的映射里（`rt.maps.anon_exec` / `rt.memfd`）。
2. **函数入口字节必须等于磁盘字节**：LSPosed/LSPlant 改 `ArtMethod` 的 quick entry、Frida Interceptor 改首几条指令，都会让「运行时字节 == 磁盘字节」不成立（`rt.maps.file_integrity` / `inj.elf.inline` / `rt.art.entrypoint`）。
3. **GOT/PLT 落点必须在合法模块的 `r-x` 内**：PLT hook 引擎与 VirtualApp 的 API 重定向都要改写重定位槽，槽值一旦指向别处即破坏（`rt.got.integrity`）。
4. **`TracerPid` 必须为 0**：任何 ptrace 注入（frida-server、gdb、调试器）都会让内核在 `/proc/self/status` 里写下 tracer（`rt.tracerpid`）。
5. **签名链与 APK 内容必须等于构建期期望**：重打包/换签/往包里塞东西，必改签名块或 ZipEntry 顺序（`pkg.signature` / `pkg.zip.fingerprint` / `pkg.codepath.hash`）。

把上表按列读，会看到**不同框架撞同一条向量**（Frida 与 Zygisk 都破坏 `rt.maps.file_integrity`），而**同一框架撞多条互不相干的向量**（Frida 同时撞 `rt.tracerpid`、`rt.maps.anon_exec`、`inj.loader.solist`）。这两个性质合起来就是「通吃」：

- 前者意味着**新增框架不需要新增向量**——这是 53 条向量能覆盖到我们没见过的框架的原因；
- 后者意味着**对手要同时让多条等式重新成立**，成本随向量数线性甚至超线性上升（`rt.tracerpid` 要撤掉 ptrace，`rt.maps.anon_exec` 要把代码搬进已映射的合法 `.so`，`inj.loader.solist` 要把模块注册进 linker 并给真实路径——三者互斥的成本远高于任一单项）。

**唯一的「框架名相关」位置**是框架适配器的 `hints()`（契约 §5）：它只产出 tier C 的包名/端口/线程名线索，作用是把 SUSPECT 的 `evidence` 写得更可读（「看起来像 Frida gadget」），**不影响是否 TAMPERED**。这条硬约束的作用是防止项目退化成「特征匹配大全」——`04-契约.md` §5 原文：适配器永远不能把 tier C 提升成 TAMPERED。
