# 第一部分 · App 交互

## 1. 现状与问题

v0.1 是「一屏到底 + 底部三个按钮」：分数、类别卡、45 条向量全部排在一条长列表里。
问题很具体：

| 问题 | 后果 |
| --- | --- |
| 45 条向量平铺 | 想找那条红的要滑到底，滑到就忘了自己在找什么 |
| 没有详情 | 看到 `rt.maps.file_integrity = TAMPERED`，但看不出「这意味着什么、要不要管」 |
| 三个按钮语义重叠 | `复制 JSON` / `导出文件` 对普通用户没意义 |
| 没有历史 | 改一版补丁重测，只能靠自己记上次多少分 |
| 自检与环境混排 | 想单独看「设备脏不脏」（Momo 那个视角）得自己数 |

## 2. 信息架构（目标）

```
TopAppBar  「试金石」                    [⟳ 刷新] [⋮ 更多]
─────────────────────────────────────────────────────────────
HeroCard   环形分数 + 状态句 + 「较上次 +2.3 ↗」
─────────────────────────────────────────────────────────────
Segmented  [ 总览 ] [ 向量 45 ] [ 环境 12 ]
─────────────────────────────────────────────────────────────
总览页     统计胶囊 → 六张类别卡（点卡片 → 跳到向量页并预置该类别筛选）
向量页     筛选 chips（全部/篡改/可疑/未判）+ 搜索框 + 分组列表
              └ 点一行 → 底部详情卡
环境页     只看 priv.* / virt.* / env.* 三类，按「设备干净度」重新组织
─────────────────────────────────────────────────────────────
FAB        右下角圆形按钮：重新检测（检测中变成转圈 + 顶部 2dp 进度条）
```

历史不是第四个 tab，而是 Hero 卡下方的一行「最近 5 次」横向小卡（分数 + 相对时间 + delta），
点一下切到那次的结果，长按删除。理由：历史是**上下文**，不是目的地。

## 4. 详情卡（最重要的一屏）

点向量行的任意位置 → 从底部升起一张卡（`Dialog` + `Window` 底部对齐 + 圆角 28dp 顶部），内容：

```
──────────────────────────────────────────
  rt.maps.file_integrity            [TAMPERED]
  运行时完整性 · tier A · 权重 5
──────────────────────────────────────────
  判据     已映射 .so 的 r-x 段字节 vs 磁盘文件
  证据     ownBad=2 e0=liblitmusprobe.so!open +0x4
  意味着   代码段被改过。正常加载不会改到已映射的 .so 正文。
  怎么绕过  要么把 trampoline 放进匿名页（但会踩 rt.maps.anon_exec），
            要么改 GOT（踩 rt.got.integrity），要么卸掉本条向量——
            三条路成本都比「不改」高，这就是不变量检测的意义。
──────────────────────────────────────────
           [ 复制这一条 ]      [ 关闭 ]
──────────────────────────────────────────
```

「判据 / 意味着 / 怎么绕过」三段文案**不许硬编码在 UI 里**，必须来自 `schema/vectors.json`
的 `zh` / `plain` / `bypass` 字段（由 `tools/gen_vector_docs.py` 生成 `VectorDocs.java`）。
这样报告和 App 永远是同一套说法。

# 第二部分 · 报告（给人看的）

## 6. 问题

v0.1 的 `report.md` / `report.html` 是**表格堆砌**：六类分数表 + 47 行向量表 + 两个列表。
机器读得懂，人读不懂。具体缺：

- 没有一句话结论（要自己从 6 个数字里推断）
- 没有「这次改了什么」的证据叙述（签名/哈希的 expect vs actual 埋在 JSON 里）
- 每条红/黄没有解释，不知道要不要关心
- 没有「下一步该做什么」
- 盲区有名字但没说「这意味着什么」

## 7. 结构（md 与 html 必须一致）

```
① 一句话结论        3 行以内，直接说「被改没改 + 哪类失守 + 哪类失明」
② 三个数字          分数 / 盲区类数 / 误报条数（大字号）
③ 这次改了什么      包状态 + 签名/哈希/指纹的 expect vs actual（表格 3 行）
④ 逐类判断          六类各一段人话（2–4 句）+ 该类关键向量（只列非 CLEAN 的）
⑤ 被坐实的问题      每条 TAMPERED：判据 / 证据 / 意味着什么 / 怎么修
⑥ 我们看不见的地方  盲区：类别 / 为什么可能是洞 / 怎么验证是不是洞
⑦ 环境噪声          与基线对比的 SUSPECT 变化，说明「这是设备脏，不是你的锅」
⑧ 怎么让分数上去    行动清单，按性价比排序，每条给「预计 +x 分」
⑨ 附录              完整向量表 + 复现命令 + 原始 JSON 路径
```

## 8. 文风要求（可验收）

| # | 要求 | 反例 |
| --- | --- | --- |
| R1 | 结论先行，第一屏就给判断 | 先放 47 行表格，结论在第 300 行 |
| R2 | 每个数字都带一句解释 | 「包完整性 36.1」→ 要写「六类里最差的一类，5 条被坐实」 |
| R3 | 不出现裸 `TAMPERED` / `CLEAN` 字样而不解释 | 要写成「被坐实（TAMPERED）」 |
| R4 | 每条红都给「意味着什么 + 怎么修」 | 只给证据串 |
| R5 | 盲区要写「怎么验证是不是洞」 | 只写「blindSpot: virtualization」 |
| R6 | 行动清单必须带预估收益 | 「提升包完整性」 |
| R7 | 全文中文，术语首次出现给英文括号 | 「盲区（blind spot）」 |
| R8 | 没有实测数字的地方标「待实测」，不许编 | 编一个「预计提升 12.3 分」 |

## 9. 生成方式（实现约束）

- **单文件**：`report.md` + 自包含 `report.html`（内联 CSS，无外链、无 `<script>`、无字体 CDN）
- 文案全部由 `litmus_narrative.py` 生成，**禁止把长句硬编码进模板字符串**——
  按类别 / 按 tier / 按 verdict 组装，保证换一条向量也能读通顺
- 「意味着什么」取自 `schema/vectors.json` 的 `plain`；「怎么修」取自 `bypass` / `fix`
- 预估收益 = `100 - 当前分类分` 按权重折算，**标注为估算**
- `selftest` 必须新增 ≥10 条断言覆盖：结论句生成、R3（无裸词）、R5（盲区带验证方法）、
  R6（行动清单带收益）、HTML 无外链

## 10. 终端输出也要人话

`litmus.py run` 结束时终端保留现有表格，但在表格**上方**加 3 行：

```
结论：这个包被改过（签名与内容都不符），包完整性被坐实 5 条；
      但注入与运行时两线一条都没抓到 —— 见「盲区」。
建议：先看 ⑥ 盲区，再看 ⑤ 被坐实的问题。
```

# 第三部分 · 还没满足的（v0.3 backlog）

报告生成器在落地九段结构后，提出了 6 个「缺了它就不敢下笔」的字段。按收益排序，
**这些是下一步最该补的契约扩展**（现在没做，所以 §7 的 ⑤⑦ 还只能贴机器串）：

| # | 字段 | 放在哪 | 缺了会怎样 | 收益 |
| --- | --- | --- | --- | --- |
| 1 | `evidence_format` | `vectors.json` 每条 | ⑤ 只能原样贴 `ownBad=2 e0=/data/…:open +0x4`，读者不知道 `e0`/`ownBad` 是什么 | **最大**：能把机器串改写成「期望签名 A，实际是 B」 |
| 2 | `score.thresholds` | `vectors.json` 或 `run.json.score` | ① 只能说「被改过」，说不出「该不该慌 / 严重到什么程度」 | 高：结论句的第一句话就该是它 |
| 3 | `impact` | `vectors.json` 每条 | `plain` 讲的是技术后果，⑤ 缺一句「所以攻击者能做到什么」 | 高：把技术翻译成业务 |
| 4 | `signal.raw` | App 侧上报 | 引用量化信息时只能转述 evidence 那句话 | 中 |
| 5 | `run.deviceState` | run.json | ⑦ 只能说「多半是环境噪声」，不能断言「这台是 MuMu + permissive」 | 中 |
| 6 | `signal.previousVerdict` | run.json | 结论句能写「比上次多抓到 2 条」，现在必须用户先给 `--baseline` | 中 |

两个顺手要收口的：

- `zh` / `plain` / `bypass` 里目前混用了裸词 `CLEAN` / `SUSPECT`，报告侧做了 `gloss_verdicts()` 兜底改写，
  但**源头应当统一**成「中文（VERDICT）」形式（规范 R3）。
- `bypass` 是「对手怎么绕过」，报告 ⑤ 的「怎么修」是把它翻成防守语气用的。若要把两者严格区分，
  需要再加 `defense` 字段；在此之前 `bypass` 一字段两用，措辞上不要写成「你应该…」。
